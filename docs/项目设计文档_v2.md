| Detection 坐标系 | 未声明 | **std_msgs/Header + 显式 world frame + 标定方法与误差记录** |

## 1. 项目定位

**一句话**：ROS2 多机器人任务调度与监控系统。多台机器人通过 Nav2 执行任务，调度中心完成任务分配、超时重试与故障恢复，Qt 控制台实现任务与机器人状态监控。

**核心卖点（按重要性排序）**：

1. **任务调度** —— 任务生成、去重、最近空闲优先分配、超时重试、失败重分配
2. **机器人状态机** —— 任务级与机器人级双层状态机，迁移条件明确、可测试
3. **ROS2 通信建模** —— 话题/服务/动作三件套各自用在对的场景，QoS 有依据
4. **多机隔离** —— namespace、TF 前缀、Nav2 多实例、桥接条目隔离
5. **故障恢复** —— 五类故障可注入、可观测、可恢复，有量化指标
6. **监控与回放** —— Qt 控制台 + RViz + rosbag 回放

**辅助手段（不作为卖点）**：OpenCV 颜色识别用于任务发现与末端精对位；Nav2 承担全部路径规划与运动控制。

**明确不做**：SLAM 在线建图、动态避障算法、深度学习检测、真机联调、Web 平台。

### 分层职责与禁止事项

| 层 | 包 | 职责 | 禁止 |
|---|---|---|---|
| 仿真 | fleet_bringup | world/models/bridge/launch/rviz/map | 不含业务逻辑 |
| 接口 | fleet_msgs | msg/srv/action | 不依赖业务包 |
| 定位导航 | Nav2（第三方） | 路径规划、运动控制、costmap | 不改造 Nav2 内部算法 |
| 感知 | fleet_perception | 图像 → Detection | 不发控制指令 |
| 执行 | robot_agent | 封装 Nav2、任务状态机、精对位、上报 | 不做全局分配 |

| 测试 | fault_injector | 按服务触发注入故障 | 不参与正常流程 |

## 4. 仿真环境改造

### 4.1 世界：从"空"到"可用于导航"

v1 的 `fleet_empty.sdf` 无墙体，激光看不到任何东西，costmap 全空 —— Nav2 能跑但无意义，且**无法注入"导航失败"故障**。改造为 `fleet_tasks.sdf`：

- 20m × 20m 场地，四周墙体 + 3 处内部隔断（形成走廊与死角，便于构造规划失败）
- 3 个 0.2m 高饱和色立方体：红 (2.5, 1.5)、绿 (4.0, -1.2)、蓝 (1.5, 3.0)
- 地面浅灰，避免与物块颜色混淆
- 世界名仍为 `fleet`

### 4.2 机器人加相机

在 `models/robotN/model.sdf` 的 `base_scan` 同级新增：

```xml
<link name="camera_link">
  <sensor name="rgb_camera" type="camera">
    <topic>robotN/camera/image</topic>
    <gz_frame_id>robotN_camera_link</gz_frame_id>
    <update_rate>15</update_rate>
    <camera>
      <horizontal_fov>1.047</horizontal_fov>   <!-- 60° -->
      <image><width>640</width><height>480</height><format>R8G8B8</format></image>
      <clip><near>0.05</near><far>10</far></clip>
    </camera>
  </sensor>
</link>
```

- 安装位置：车头前方 0.05m、高 0.15m、俯角 12°（保证 0.5–3m 的物块落在画面下 1/3）
- URDF 同步增加 `camera_link` / `camera_joint`（launch 里的前缀化函数自动处理）
- 理由：选 RGB 而非 RGBD —— 软件渲染下深度相机开销大，单目测距 + 已知物块尺寸已满足精对位需求，且原理更易讲清

### 4.3 定位方案（关键取舍）

Nav2 需要 `map → odom → base_link` 变换链。两种方案：

| 方案 | 做法 | 风险 | 选择 |
|---|---|---|---|
| **A. 已知初始位姿（默认）** | 静态 TF `map → robotN_odom` 取出生位姿，map 帧即世界坐标系 | 低，确定性好，测试可复现 | ✅ 默认 |
| B. AMCL | 每车起 AMCL 在共享地图中定位 | 中，空场地特征少易漂移，调试成本高 | 文档化，作为可选扩展 |

> 采用 A 的理由：仿真里程计无噪声，已知初始位姿下定位是精确的；把精力留给调度与故障恢复。方案 B 的具体配置在文档中保留，作为"若要做真实定位"的升级路径。
>
> 注意：v1 的 `world` 帧改名为 `map`，以符合 Nav2 惯例；两条静态 TF 的坐标值与之前相同。

### 4.4 地图

- 用 `map_server` 加载 `fleet_bringup/maps/fleet_map.{pgm,yaml}`：20×20m 场地 + 墙体，与 SDF 几何一致
- 分辨率 0.05 m/px，原点 (-10, -10)
- 生成方式：按 SDF 墙体坐标手写生成脚本 `scripts/gen_map.py`（可复现），不依赖在线建图

### 4.5 启动编排（重建）

`fleet_sim.launch.py` 结构：

```
SetEnvironmentVariable(GZ_SIM_RESOURCE_PATH)
SetParameter(use_sim_time:=True)
DeclareLaunchArgument: gui(false) rviz(true) perception(true) nav2(true) console(true) record(true)
① gz sim -r -s  world
② gz sim -g       (gui:=true 时)
③ ros_gz_bridge   (config_file:=bridge.yaml)
④ map_server (全局，单实例，/map)
⑤ 每车: robot_state_publisher(去前缀 URDF) + 静态 map→odom TF + spawn
⑥ 每车: Nav2 栈 (namespace:=robotN, params_file:=nav2_robotN.yaml)
⑦ 每车: robot_agent, fleet_perception
⑧ fleet_manager
⑨ RViz2 (TimerAction 6s 后，避免 TF 未就绪时相机初始化错位)
⑩ rosbag2 record（按需）
```

- fleet_console 单独命令启动（Qt 进程与仿真解耦，便于独立重启）
- `nav2_robotN.yaml` 中所有话题以 `robotN/` 为前缀，`use_sim_time: true`

### 4.6 RViz 配置

两个 RobotModel + 两路 Image + 两个 LaserScan + 两个 Odometry + TF + Grid + `/fleet/task_markers`（MarkerArray），Fixed Frame `map`。

## 5. 接口设计（fleet_msgs）

> 修订要点：任务分配改为**调度器直调每车 action**，`/fleet/tasks` 降级为**只读监控广播**（agent 不订阅，仅 console/RViz/rosbag 订阅）。这样"两台车同时执行同一任务"在通信层就不可能发生，不需要乐观锁。

### 5.1 消息

**Task.msg**（监控视图，由调度器单向发布）

```
uint8 TYPE_APPROACH=1
uint8 TYPE_INSPECT=2

string task_id
uint8  type
uint8  target_color            # 1=RED 2=GREEN 3=BLUE
geometry_msgs/Pose target_pose

# 分配信息（供监控显示任务归属）
string assigned_robot_id       # 空 = 未分配
uint64 revision                # 每次状态变更 +1，供监控判断时序/丢弃过期包

# 时间与重试（供监控与超时判断）
builtin_interfaces/Time detected_at    # 目标首次被检测到的时间
builtin_interfaces/Time assigned_at    # 最近一次分配时间，未分配为 0
uint8  retry_count                     # 已重试次数
uint8  max_retries                     # 上限，默认 1
```

**TaskStatus.msg**（agent → 调度器/监控）

```
uint8 STATE_PENDING=0
uint8 STATE_ASSIGNED=1
uint8 STATE_NAVIGATING=2
uint8 STATE_DOCKING=3
uint8 STATE_DONE=4
uint8 STATE_FAILED=5
uint8 STATE_CANCELED=6

string task_id
string robot_id
uint8  state
float32 progress               # 0.0~1.0
string detail                  # 当前动作描述
string failure_reason          # 失败原因，枚举字符串：
                               # NAV_TIMEOUT / NAV_ABORTED / TARGET_LOST
                               # / DOCK_TIMEOUT / ROBOT_UNREACHABLE / CANCELED_BY_OPERATOR
uint8  retry_count             # 与 Task 同步，便于监控对齐
builtin_interfaces/Time detected_at    # 任务来源时间（透传）
builtin_interfaces/Time stamp
```

**RobotStatus.msg**

```
uint8 STATE_IDLE=0
uint8 STATE_BUSY=1
uint8 STATE_ERROR=2
uint8 STATE_OFFLINE=3         # 由调度器按心跳超时置位

string robot_id
uint8  state
geometry_msgs/Pose2D pose
string current_task            # 空 = 无
uint16 tasks_done
uint16 tasks_failed
uint32 heartbeat_seq           # 递增序号，供调度器判活
builtin_interfaces/Time stamp
```

**Detection.msg**（修订：加 Header，明确坐标系）

```
std_msgs/Header header         # header.stamp = 图像时间戳
                               # header.frame_id = "map"（world_pose 所在坐标系，显式声明）
uint8 COLOR_RED=1
uint8 COLOR_GREEN=2
uint8 COLOR_BLUE=3

string source_robot_id
uint8  color
float32 confidence             # 轮廓面积 / 参考面积，>1 表示偏大
sensor_msgs/RegionOfInterest bbox   # 像素坐标，基于与 header.stamp 同时刻的图像
geometry_msgs/Point world_pose      # 目标在 map 系下的估计位置（含 z 高度）
float32 range                  # 单目测距结果（米）
float32 bearing                # 相对光轴水平偏角（弧度）
float32 range_sigma            # 本次测距的不确定度估计（由像素宽反推，见 §7.3）
```

> `world_pose` 的 frame 由 `header.frame_id` 唯一确定，不隐式依赖 odom；`bbox` 是图像像素坐标，通过 `header.stamp` 与图像对齐。两者语义分离，消费方不会误用。

### 5.2 服务

**SubmitTask.srv**（测试/演示注入任务）

```
uint8 target_color
geometry_msgs/Pose target_pose
---
bool accepted
string task_id
string message
```

**CancelTask.srv**

```
string task_id
string reason                  # 记录取消原因，写入 TaskStatus.failure_reason
---
bool canceled
string message
```

### 5.3 动作

**ExecuteTask.action**（robot_agent 提供，**fleet_manager 每车一个 action client 直接调用**）

```
# Goal —— 一次调用 = 一个任务的全部执行过程
string task_id
uint8  target_color
geometry_msgs/Pose target_pose
float32 standoff               # 期望停车距离，默认 0.6m
---
# Result
bool   success
string failure_reason          # 与 TaskStatus.failure_reason 同枚举
float32 final_distance
float32 final_heading_error
---
# Feedback
uint8   state                  # 复用 TaskStatus 的状态常量
float32 distance_remaining
float32 progress
string  detail
```

**为什么用每车独立 action 调用，而不是广播订阅**：

| | 广播 + 各车自判 | 每车 action 直调 |
|---|---|---|
| 互斥性 | 靠字段协商，可能双执行 | goal 只能被一个 server 接受，**结构上互斥** |
| 归属明确 | 需要乐观锁/revision 仲裁 | `assigned_robot_id` 就是被调用的那台 |
| 失败感知 | 靠超时猜 | action result 直接带回失败原因 |
| 取消 | 广播取消消息 | action cancel 原生支持 |

`revision` 字段保留，但用途改为**监控端的时序判序与过期丢弃**，不是并发控制手段。

### 5.4 话题与 QoS 设计

| 话题 | 类型 | QoS | 依据 |
|---|---|---|---|
| `/robotN/odom` `/scan` `/imu` | 传感器 | `SensorDataQoS`（BestEffort, KeepLast 5） | 高频流式，丢一帧无害，Localhost 下延迟更低 |
| `/robotN/camera/image` | 图像 | BestEffort, KeepLast 1, Depth 1 | 只关心最新帧，背压会让仿真变慢 |
| `/robotN/status` | RobotStatus | Reliable, KeepLast 10 | 状态不允许丢，低频 |
| `/fleet/tasks` | Task | Reliable, **TransientLocal**, KeepLast 20 | 监控端可能后加入，需要拿到当前任务表快照 |
| `/fleet/task_status` | TaskStatus | Reliable, KeepLast 50 | 用于审计与回放，允许积压 |
| `/fleet/task_markers` | MarkerArray | Reliable, KeepLast 1 | 可视化为瞬时快照 |
| `/robotN/cmd_vel` | Twist | Reliable, KeepLast 5 | 控制指令 |
| Nav2 内部话题 | — | 沿用 Nav2 默认 | 不覆盖第三方默认，除非有明确理由 |

**已知 QoS 风险**：`ros_gz_bridge` 默认发布为 Reliable，而 Nav2 costmap 的 scan 订阅通常为 BestEffort —— 需在 M1 用 `ros2 topic info -v` 逐条核对，若不适配则在 bridge.yaml 中显式指定，或让 Nav2 侧参数与桥一致。此项列为 M1 验收项。

## 6. 任务模型与状态机

### 6.1 双层状态机

```
【任务生命周期】
  PENDING ──分配──▶ ASSIGNED ──agent接受──▶ NAVIGATING ──到达──▶ DOCKING ──对位完成──▶ DONE
     ▲                  │                      │                  │
     │                  │ 拒绝/超时             │ 导航失败          │ 对位超时
     │                  ▼                      ▼                  ▼
     └──重排(retry<max)─┴──────────────── FAILED / CANCELED
                        （retry≥max 时终态 FAILED）

【机器人生命周期】
  IDLE ──接任务──▶ BUSY ──任务结束──▶ IDLE
    ▲                │
    │                │ 连续失败 ≥2 或心跳异常
    └──人工/服务重置── ERROR / OFFLINE
```

### 6.2 迁移条件（每条都可写 gtest）

| 从 | 到 | 触发条件 |
|---|---|---|
| PENDING | ASSIGNED | 调度器选定空闲车并发出 goal 且被接受 |
| PENDING | FAILED | 无可用车且等待超过 `assign_timeout`(30s) |
| ASSIGNED | NAVIGATING | agent 回第一个 feedback |
| NAVIGATING | DOCKING | 距目标 < `dock_entry_distance`(1.2m) |
| NAVIGATING | FAILED | Nav2 result 失败，或耗时 > `nav_timeout`(60s) |
| DOCKING | DONE | 横向误差 < 5cm 且距离误差 < 10cm |
| DOCKING | FAILED | 连续 15 帧无检测且重试搜索 3 次仍失败，或 > `dock_timeout`(30s) |
| FAILED | PENDING | `retry_count < max_retries`（默认 1） |
| 任意 | CANCELED | 收到 CancelTask，`reason` 记入失败原因 |
| BUSY | ERROR | 连续 2 次任务失败 |
| 任意 | OFFLINE | 调度器 `now - last_heartbeat > 3s` |

### 6.3 分配算法

```
触发: 新 PENDING / 机器人转 IDLE / 任务超时重排
候选: 所有 IDLE 机器人
代价: 到目标的欧氏距离
选优: 最小代价; 平局按 robot_id 字典序（保证可复现）
约束:
  - 一车同时仅一个任务（由 action 单 goal 语义保证）
  - 两任务目标距离 < 1.0m → 后者等待（避免抢同一物块）
  - 目标不可达（Nav2 规划失败）→ 换车重试一次，仍失败则 FAILED
```

### 6.4 并发与线程模型

- `fleet_manager`：`MultiThreadedExecutor`，但**回调只投递事件到队列**，状态变更集中在单线程 `drainEvents()` 中处理（表加互斥锁）
- `robot_agent`：动作 server 单 goal（`goal_handle` 拒绝新 goal），状态机在其内部串行推进
- 理由：避免"回调里改状态、多线程交叉"导致的竞态，这一设计会在文档中明确写出，并作为面试可讲的点

## 7. 感知设计（OpenCV，辅助手段）

### 7.1 流水线

```
Image(640×480, BestEffort)
  → cv_bridge
  → resize 到 320×240
  → BGR→HSV
  → 三色 inRange（红=两段 H 合并）
  → 开运算去噪 + 闭运算补洞（5×5，各 1 次）
  → findContours，面积 ≥ 200px²
  → 每色取最大轮廓
  → 质心(u,v) + 外接框宽 w
  → 单目测距 + 方位角
  → 时序去抖（连续 3 帧一致）
  → 发布 Detection（header.frame_id = "map"）
```

### 7.2 颜色阈值（初值，写入 config/perception.yaml，可在线调）

| 颜色 | H | S | V |
|---|---|---|---|
| 红 | 0–10 ∪ 170–180 | 120–255 | 70–255 |
| 绿 | 40–80 | 100–255 | 60–255 |
| 蓝 | 100–130 | 120–255 | 60–255 |

### 7.3 单目测距与不确定度

```
f = (W_img / 2) / tan(HFOV / 2)           # 640/2 / tan(30°) ≈ 554 px
range   = f * W_block / w_pixels           # W_block = 0.2m
bearing = atan((u - cx) / f)
σ_range ≈ range * (Δw / w)                 # Δw≈2px 由轮廓离散化决定
                                         # 0.6m 处 σ≈0.005m；3m 处 σ≈0.027m
world_pose = T_map_robot ⊗ T_robot_camera ⊗ (range, bearing)
```

- 有效区间：0.5–5.0m（对应像素宽 22–220px），越界丢弃
- 不确定度随距离线性增长，写入 `range_sigma` 供调度器做加权判断

### 7.4 标定方法与误差记录

1. **内参**：直接取 `camera_info`（仿真相机给出的理论内参），与上式计算的 `f` 交叉核对，偏差应 < 2%
2. **外参**：来自 URDF `camera_joint`（精确值，无需标定），安装偏差通过 M4 静态标定实验记录
3. **静态标定实验**（M4 验收产出）：把物块放在 1.0 / 2.0 / 3.0m 三个已知位置，记录 `world_pose` 与真值偏差，形成表格

| 真实距离 | 测距均值 | 测距误差 | 横向误差 | 样本数 |
|---|---|---|---|---|
| 1.0m | 待测 | 待测 | 待测 | 100 |
| 2.0m | 待测 | 待测 | 待测 | 100 |
| 3.0m | 待测 | 待测 | 待测 | 100 |

> 表格数据在 M4 阶段用实际运行结果填充，作为"指标是否真实"的证据。

## 8. 执行设计（robot_agent）

### 8.1 职责

1. **封装 Nav2**：持有 `NavigateToPose` action client，把任务的 `target_pose` 转成 Nav2 goal（含 `standoff` 处理后目标），转发 Nav2 feedback 为自己的 feedback
2. **任务状态机**：驱动 §6.2 的迁移
3. **视觉精对位**：Nav2 到达后，用 Detection 做小范围视觉伺服（横向 ±20cm），解决"Nav2 定位精度不足以精确对位"的问题
4. **上报**：RobotStatus 心跳（1Hz）+ TaskStatus 变更即发

### 8.2 精对位（DOCKING）

```
输入: /robotN/detection 中与目标色一致的最新一条
      e_u = (u - cx) / (W_img/2)
      angular.z = clamp(-1.2 * e_u, -0.6, 0.6)
      e_d = range - standoff
      linear.x  = clamp(0.6 * e_d, -0.08, 0.12)
完成: |e_u| < 0.03 且 |e_d| < 0.10  →  DONE
保护: 控制周期 15Hz（图像帧驱动）；odom 做距离兜底
      连续 15 帧无检测 → 后退 0.3m 重搜，3 次后 FAILED(TARGET_LOST)
      超 dock_timeout(30s) → FAILED(DOCK_TIMEOUT)
```

> Nav2 负责"从 A 到 B 附近"，视觉负责"最后 20cm"。这个分工是本项目的实际工程结论，也是可讲的点。

## 9. 调度设计（fleet_manager）

### 9.1 任务生成与去重

```
收到 Detection（某车某色）
  → 查任务表：同色 且 目标距离 < 0.5m → 视为同一目标，revision+1，忽略
  → 否则创建 PENDING（task_id = 颜色缩写 + detected_at 毫秒）
  → 发布 /fleet/tasks（TransientLocal，监控端可后加入）
```

去重不依赖"哪个机器人看到的"，只用颜色 + 空间距离 —— 避免同一物块被两车分别发现后生成两个任务。

### 9.2 分配与调用

```
候选 IDLE 车 → 按 §6.3 选优 → 记录 assigned_robot_id, assigned_at, revision+1
  → 该车 action client 发送 ExecuteTask goal
  → goal 被接受 → 任务 ASSIGNED，机器人 BUSY
  → goal 被拒绝/超时(3s) → 该车标记不可用，换下一候选
```

### 9.3 超时与重试

- 看门狗 1Hz 扫描：`NAVIGATING/DOCKING` 超时 → 取消 goal → 任务回 PENDING（`retry_count+1`）
- `retry_count ≥ max_retries` → FAILED，`failure_reason` 记录
- 机器人心跳超时 3s → OFFLINE，其持有任务立即重排给其他车（**这是故障恢复的核心场景**）

### 9.4 Marker 发布

`/fleet/task_markers`：每个任务一个文本标签（`task_id / robot_id / state / retry`）+ 箭头指向目标，颜色编码状态（灰=待分配，黄=执行中，绿=完成，红=失败）。

## 10. 故障注入与恢复（fault_injector）

独立节点，**全部通过服务触发**，可脚本化、可重复、可纳入集成测试。

| 故障 | 触发方式 | 系统应表现 | 恢复验证 |
|---|---|---|---|
| **F1 目标丢失** | 服务临时把物块移出视野/暂停相机话题 | agent DOCKING 重搜 3 次后 FAILED(TARGET_LOST) | 任务回 PENDING 并成功重试 |
| **F2 导航失败** | 服务把目标点设到墙内/不可达区域 | Nav2 规划失败 → FAILED(NAV_ABORTED) | 换车重试或终态 FAILED，Marker 变红 |
| **F3 机器人离线** | 服务 kill 某车 agent 进程（或停其状态发布） | 3s 内该车转 OFFLINE，其任务 5s 内重分配给另一车 | 重启 agent 后回到 IDLE，可再接任务 |
| **F4 任务超时** | 服务把 `nav_timeout` 临时调到 3s | 超时取消 → retry → 成功或 FAILED | 指标可查（重试次数、耗时） |
| **F5 重分配** | 服务提交一个双车竞争场景 | 最近空闲优先选中正确车，另一车保持 IDLE | 归属唯一，action 层面互斥 |

配套：
- `scripts/demo_faults.sh`：按顺序注入 5 类故障并打印系统响应，用于演示与回归
- 每类故障记录：**检测时延、恢复时延、是否成功**，形成故障恢复指标表

## 11. 监控设计

### 11.1 Qt6 控制台（fleet_console）

**架构约定（关键）**：ROS2 与 Qt 在同一进程的不同线程 —— ROS2 节点在**独立线程** spin，UI 在**主线程**；ROS 线程收到消息后通过 Qt 信号槽（`Qt::QueuedConnection`）投递到 UI 线程更新控件。**禁止**在 ROS 回调里直接操作 UI 控件。

```
fleet_console 进程
├── 主线程: QApplication + MainWindow
│     ├── 任务列表 QTableView    ← /fleet/tasks + /fleet/task_status
│     ├── 机器人状态表            ← /robotN/status
│     ├── 告警区 QListView        ← OFFLINE / FAILED / 重试事件
│     ├── 日志区 QPlainTextEdit   ← /rosout（按 task_id/robot_id 过滤）
│     └── 相机画面 QLabel ×2      ← /robotN/camera/image（可关，省 CPU）
└── ROS 线程: rclcpp::Node(spin)
      ├── 订阅 /fleet/tasks, /fleet/task_status, /robotN/status,
      │        /robotN/camera/image, /rosout
      ├── 调用 CancelTask 服务（UI 上"取消任务"按钮）
      └── 调用 fault_injector 服务（UI 上"注入故障"下拉菜单）
```

功能范围（刻意收敛，不做大而全平台）：

- 任务列表：ID / 颜色 / 归属车 / 状态 / 重试次数 / 耗时，可右键取消
- 机器人状态：ID / 状态 / 当前位置 / 当前任务 / 成功失败计数 / 心跳
- 告警区：OFFLINE、FAILED、重试、超时
- 日志区：关键字过滤
- 相机画面：可开关
- 回放入口：按钮启动 `ros2 bag play` 并显示进度（读取 bag 元信息）

### 11.2 RViz（并行保留）

模型 / 激光 / 里程计 / 两路相机 / 任务 Marker，Fixed Frame `map`。用于调试与截图证据。

### 11.3 rosbag 回放

- 录制：`/fleet/*`、`/robotN/status`、`/robotN/odom`、`/robotN/detection`、`/rosout`
- 回放测试：离线重放 bag，验证 `fleet_manager` 能在重放数据上复现出相同的任务序列（见 §12.4）

## 15. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| **Nav2 多机 namespace 配置复杂** | 高 | M2 提前验证；先跑通单车再复制；参数文件按车生成；失败则退回"单车完整 + 第二车仅状态展示"的降级方案 |
| Nav2 在 18G/16 核 VM 上跑双实例资源不足 | 中 | 关闭 gui；RViz 延迟启动；降 costmap 分辨率；必要时控制器降到 10Hz |
| bridge 与 Nav2 的 QoS 不兼容 | 中 | M1 显式检查 `ros2 topic info -v`；必要时在 bridge.yaml 指定 QoS 或调整 Nav2 参数 |
| 相机在软件渲染下掉帧 | 中 | 处理降到 320×240；相机 15Hz；控制台相机画面可关 |
| 视觉测距受俯角/物块朝向影响 | 中 | M4 静态标定实验量化误差；写入 `range_sigma`；精对位只用相对变化，不用绝对精度 |
| Qt 与 ROS 线程冲突 | 中 | 强制"ROS 线程 spin / UI 主线程 / 信号槽 QueuedConnection"架构，不混用 |
| 状态机竞态 | 中 | 回调只投递事件、单线程处理、表加锁；状态机纯逻辑可单测 |
| 故障注入影响正常演示 | 低 | fault_injector 独立节点，默认不启动；演示脚本显式拉 |
