# 多机任务调度与监控系统 · 交付文档

- 版本：v1.0（M9 交付）
- 作者：赵威（enenr2）
- 代码仓库：`github.com/enenr2/ROS2-Multi-Robot-Task-Scheduling-and-Monitoring-System`
- 运行环境：Ubuntu 26.04 + ROS 2 Lyrical + Gazebo Sim 10 + Nav2 1.5.2 + Qt6

---

## 1. 交付概览

默认两台、可扩展至五台 TurtleBot3 在 Gazebo 中自主作业，完整链路为：

**视觉发现彩色目标 → 调度中心建单并分配 → Nav2 导航到目标附近 → 视觉闭环精对位停车 → 状态回写与监控**

| 里程碑 | 内容 | 状态 |
|---|---|---|
| M0–M2 | 接口层、仿真底座、Nav2 单机导航 | 完成 |
| M3–M6 | 调度核心、感知、执行代理、ROS 适配与自动闭环 | 完成 |
| M7 | 四类故障注入 + AMCL 共享定位 | 完成 |
| M8 | Qt6 监控台（任务/车辆/告警/日志/相机/回放） | 完成 |
| M9 | 集成测试、回放固化、Docker、CI、交付文档 | 完成 |

核心卖点：任务调度、状态机、ROS 2 通信建模、多机隔离、故障恢复。导航交给 Nav2，
视觉只用于目标发现与对位，避免"用视觉做导航"的不稳定实现。

## 2. 系统架构

```
Gazebo Sim 10（fleet_tasks.sdf，20×20 m 场地 + 3 个彩色物块）
   │  ros_gz_bridge
   ├── /robotN/odom /scan /imu /cmd_vel /camera/image ...
   │
   ├── fleet_perception（每车一个）
   │     HSV 分割 → 单目测距 → 时序去抖 → TF 转 map 系 → /robotN/detections
   │
   ├── Nav2 + AMCL（每车一套，命名空间隔离）
   │     map → robotN_odom 由 AMCL 动态发布
   │
   ├── fleet_agent（每车一个）
   │     execute_task action：导航 → 对位 → 停车，发布 task_status / robot_status
   │
   └── fleet_manager（全局一个）
         订阅 detections / 状态 / 心跳，建单、分配、看门狗、重试与改派
         发布 /fleet/tasks 快照与 /fleet/task_markers，提供 submit/cancel 服务
              │
              └── fleet_gui（Qt6 监控台，可独立启停）
                    任务表 / 车辆表 / 告警 / 日志 / 地图 / 相机 / rosbag 回放
```

分层原则：**能脱离 ROS 的数学与状态逻辑一律做成纯 C++ 库**，用注入时间驱动单测；
ROS 节点只做接线与消息转换。

## 4. 接口契约

### 4.1 话题

| 话题 | 类型 | 方向 | 说明 |
|---|---|---|---|
| `/fleet/tasks` | `fleet_msgs/Task` | manager → 全局 | 任务快照，0.5 s 全量重发，`revision` 单调递增 |
| `/fleet/task_markers` | `MarkerArray` | manager → RViz | 任务目标点可视化 |
| `/robotN/detections` | `fleet_msgs/Detection` | perception → manager | map 系目标位置、测距、`lost` 丢失标志 |
| `/robotN/task_status` | `fleet_msgs/TaskStatus` | agent → manager / GUI | 状态事件，含进度、失败原因、重试次数 |
| `/robotN/robot_status` | `RobotStatus` | agent → manager / GUI | 1 Hz 心跳，含位姿、当前任务、完成/失败/取消计数 |
| `/robotN/camera/image` | `sensor_msgs/Image` | 桥 → perception / GUI | 320×240，软件渲染下约 4~5 Hz |
| `/map` | `nav_msgs/OccupancyGrid` | map_server → Nav2 / GUI | transient_local，20×20 m，0.05 m/px |

### 4.2 服务

| 服务 | 请求 | 响应 | 说明 |
|---|---|---|---|
| `/fleet/submit_task` | 颜色 + 目标位姿 | `accepted` / `task_id` / `message` | 手动注入；同色同位置（<0.8 m）去重 |
| `/fleet/cancel_task` | `task_id` + 原因 | `canceled` / `message` | 取消执行中的任务并释放车辆 |

### 4.3 Action

`/robotN/execute_task`（`fleet_msgs/ExecuteTask`）：一次调用 = 一个任务全过程。

- Goal：`task_id`、`target_color`、`target_pose`、`standoff`
- Feedback：`state`、`distance_remaining`、`progress`、`detail`
- Result：`success`、`failure_reason`、`final_distance`、`final_heading_error`

失败原因枚举：`NAV_TIMEOUT` / `NAV_ABORTED` / `TARGET_LOST` / `DOCK_TIMEOUT` /
`ROBOT_UNREACHABLE` / `CANCELED_BY_OPERATOR` / `ASSIGN_TIMEOUT` / `GOAL_ACK_TIMEOUT` /
`GOAL_REJECTED` / `AGENT_FAILED`。

终态语义：

- 成功 → `succeed(result)` + `TaskStatus.DONE`
- 用户取消 → `canceled(result)` + `TaskStatus.CANCELED`、`failure_reason=CANCELED_BY_OPERATOR`，
  不计入 `tasks_failed`；`RobotStatus.tasks_canceled` 单独计数
- 失败 → `abort(result)` + `TaskStatus.FAILED` + 具体原因

`goal.standoff` 是任务级参数：agent 在任务开始时覆盖对位控制器配置并限制在 0.25~2.0 m；
未填（0/负数）时回退到 agent 启动参数。

### 4.4 关键参数

| 节点 | 参数 | 默认 | 说明 |
|---|---|---|---|
| manager | `dispatch_robot_ids` | 全部车 | 允许派活的车 |
| manager | `assigned_timeout` | 10 s | action goal 等待 agent 确认的超时 |
| manager | `nav_timeout` / `dock_timeout` | 100 / 150 s | 看门狗总预算 |
| manager | `heartbeat_timeout` | 3.0 s | 心跳超时判离线 |
| manager | `retry_cooldown` | 10 s | 失败车冷却，避免重试又派回同一台 |
| manager | `standoff` | 0.6 m | 任务级停车距离，范围 0.25~2.0 m |
| manager | `retention_age` / `retention_max_tasks` | 600 s / 500 | 终态任务保留策略，超期清理 |
| agent | `standoff` / `pre_dock_margin` | 0.6 / 0.8 m | 任务未指定 standoff 时的默认值 |
| agent | `nav_timeout` / `dock_timeout` | 90 / 45 s | 单段执行超时 |
| agent | `distance_tolerance` / `bearing_tolerance` | 0.10 m / 0.05 rad | 对位收敛门槛 |
| perception | `target_width` / `max_range` | 0.2 / 5.0 m | 单目测距先验与实际量程 |
| perception | `debounce_frames` / `lost_frames` | 3 / 15 | 时序去抖与丢失判定 |

## 5. 部署

### 5.1 本地（推荐用于开发与仿真验收）

```bash
# 依赖：Nav2、cv_bridge、Qt6、rosbag2、Docker（可选），脚本幂等
sudo bash scripts/install_deps.sh

source /opt/ros/lyrical/setup.bash
colcon build --symlink-install
source install/setup.bash

# 全量启动（含 Qt 监控台）
ros2 launch fleet_bringup fleet_sim.launch.py gui:=false rviz:=false monitor:=true
```

启动开关：`gui`（Gazebo GUI）、`rviz`、`nav2`、`perception`、`agent`、`manager`、`monitor`。
`gui:=false` 时物理仿真仍以 `-s` 服务端运行；`monitor:=true` 会在第 34 s 拉起监控台。

压测使用 `robot_count:=3` 到 `robot_count:=5`，例如：

```bash
ros2 launch fleet_bringup fleet_sim.launch.py robot_count:=5 \
  gui:=false rviz:=false monitor:=false
python3 scripts/smoke_sim.py --robot-count 5 --timeout 360 --boot-timeout 240
```

机器人逐套错峰启动 Nav2；五台时 manager 会在最后一套 Nav2 和全部 agent 拉起后再启动。五台完整相机仿真资源消耗较高，建议保持 headless，必要时设置 `perception:=false` 做纯调度/导航压力测试。

停止：

```bash
./scripts/stop_sim.sh   # SIGTERM → SIGKILL，并清理 /dev/shm/fastdds_*
```

### 5.2 Docker

```bash
docker compose build
docker compose up -d sim        # 无界面仿真，约 40 s 后 Nav2 就绪
docker compose up monitor       # 需要图形会话（X11 socket 已挂载）
```

镜像内入口：

```bash
docker run --rm --network host fleet-sim:latest sim
docker run --rm --network host fleet-sim:latest monitor --camera robot2 --tab 告警
docker run --rm --network host -v /path/bag:/bag fleet-sim:latest replay /bag
```

说明：

- 镜像基于 `ros:lyrical-ros-base`，构建阶段编译本仓库到 `/ws/install`
- 仿真使用软件渲染（`LIBGL_ALWAYS_SOFTWARE=1`），GPU 环境可去掉
- `network_mode: host` 是 DDS 发现最省事的方式；跨主机部署请改用 Fast DDS Discovery Server
- **本机开发环境无法访问 Docker Hub，镜像未在本机实际构建**；`docker compose config`
  已校验，CI 的 `docker` job 会在有网络的环境构建验证

### 5.3 CI

`.github/workflows/ci.yml` 两个 job：

| Job | 内容 | 不做什么 |
|---|---|---|
| `build-and-test` | 容器内安装依赖 → `colcon build`（跳过 bringup）→ 单测 + 集成测试 → 上传测试报告与汇总 | 不跑 Gazebo 仿真 |
| `docker` | Buildx 构建镜像（不推送） | 不跑容器 |
| `nightly-sim`（nightly-sim.yml） | 每晚/手动：headless Gazebo + 默认双机 launch + 注入任务，断言 `NAVIGATING → DOCKING → DONE`，保存 sim 日志与 bag | 不进 PR 门禁 |

为什么 CI 日常不跑 Gazebo：3D 仿真对 GPU/CPU 与稳定性要求高，跑一次要几十秒到几分钟，
失败多是环境抖动。调度/感知/代理的核心逻辑全部有纯逻辑单测；跨节点链路用
`fleet_integration` 的假 agent 覆盖；完整仿真退化由 nightly 工作流兜底。

本地复现 CI 的内容：

```bash
source /opt/ros/lyrical/setup.bash
colcon build --packages-skip fleet_bringup
source install/setup.bash
colcon test --packages-select fleet_manager fleet_perception fleet_agent fleet_gui fleet_integration \
  --return-code-on-test-failure
colcon test-result --all --verbose
python3 scripts/test_summary.py

# 端到端冒烟（先起 headless 仿真）
python3 scripts/smoke_sim.py --timeout 200
```

## 6. 运行手册

### 6.1 启动与检查

1. 启动仿真后等 `调度中心就绪` 出现；车辆数量由 `robot_count` 或 `robots` 决定。
2. 检查 Nav2：每个命名空间下 `amcl/controller_server/planner_server` 均为 `active`。
3. 打开监控台，状态栏应显示配置车辆全部在线，相机页出现画面。

```bash
ros2 node list | grep -E 'amcl|controller_server|robot_agent|fleet_manager'
ros2 topic hz /robot1/robot_status     # 约 1 Hz
ros2 topic hz /robot1/camera/image     # 约 4~5 Hz
```

### 6.2 监控台操作

| 操作 | 说明 |
|---|---|
| 相机下拉框 | 切换 `robot1/robot2`，不重启节点 |
| 地图 | 滚轮缩放、左键拖拽平移、双击恢复全图 |
| 注入任务 | 选颜色 + 坐标（或点「地图选点」后点地图）→「下发」 |
| 取消任务 | 在任务表选中一行 →「取消选中任务」；终态为 `CANCELED`，不计入失败 |
| 回放 | 「打开 rosbag…」选择目录，拖动时间轴、切换 1/2/4/8 倍速 |
| 命令行 | `--camera`、`--tab`、`--replay`、`--screenshot`/`--quit-after` |

告警判定：

- 心跳 1 Hz；超过 **2.5 s** 无心跳 → 判离线并告警
- 只发现话题、从未收到心跳的车登记为"离线占位"，2 倍超时后告警一次
- 任务失败、重排、机器人异常都会进告警页

### 6.3 故障处理

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 某车在地图上变灰、状态栏在线数减少 | `robot_agent` 崩溃/被冻住 | 查 `ps -eo pid,stat,args \| grep robot_agent`；重启仿真 |
| 任务一直 `NAVIGATING` 后失败 | 路径被挡、Nav2 卡住 | 看 `/<robot>/controller_server` 日志；看门狗会超时改派 |
| 任务 `TARGET_LOST` | 物块被移走 / 对位点偏 | 确认物块在位；agent 会自动倒车+转圈搜索一轮 |
| Nav2 一直 `Configuring xxx` | 双栈同时启动挤掉 DDS 响应 | 已用 10 s 错峰启动；仍失败则清理 `/dev/shm/fastdds_*` 后重试 |
| 某车 static TF 凭空消失 | Fast DDS 共享内存残留 | `./scripts/stop_sim.sh` 清理后重启 |
| 监控台收不到相机 | 桥未起 / 选错车 | 查 `/robotN/camera/image` 的 `ros2 topic hz` |

### 6.4 录制与回放

```bash
# 标准演示包（任务快照、心跳、状态事件、检测结果，默认 90 s）
./scripts/record_demo_bag.sh /tmp/demo_bag 120

# 回放
ros2 run fleet_gui fleet_monitor --replay /tmp/demo_bag
```

回放只读 `/fleet/tasks`、`/robotN/robot_status`、`/robotN/task_status`。
bag 里没有图像，回放期间相机页显示等待提示；sqlite3 与 mcap 两种存储都支持。

### 7.3 故障注入（每个场景独立干净仿真）

| 场景 | 注入手段 | 预期 | 结果 |
|---|---|---|---|
| A 机器人离线 | `SIGSTOP` agent | 心跳超时 `ROBOT_UNREACHABLE` → 改派 → 完成 | 通过 |
| B 任务超时 | 在线把 `nav_timeout` 缩到 2 s | `NAV_TIMEOUT` → 取消 → 改派 → 完成 | 通过 |
| C 导航栈卡死 | `SIGSTOP` controller_server | `NAV_ABORTED` → 改派 → 完成 | 通过 |
| D 目标丢失 | 对位移走物块 | `TARGET_LOST` → 重试 1 次 → `FAILED` | 通过 |

C 会让故障车的 Nav2 整栈被 lifecycle bond 下线，属于"需人工介入"的真实语义，
因此脚本把它排在最后执行。

## 8. 已知限制

- 相机在软件渲染下约 4 Hz，对位限速 0.15 m/s；激光约 2.3 Hz
- 感知每色只上报一个目标；偏轴测距系统性偏小（24° 时约 0.2 m）
- AMCL 依赖手写地图与仿真激光，真实场地需重新建图与标定
- 回放不含图像；整包读入内存，适合分钟级 bag
- 监控端任务/车辆表 500 ms 全量重建，任务数上千需换增量模型
- 终态任务保留期内（默认 10 分钟）同一位置不会重复建单；重新巡检需移动物块或等保留期过期
- 历史任务归档依赖 rosbag（`record_demo_bag.sh`），调度器只做内存保留与清理
- cmd_vel 看门狗应由底盘驱动实现；agent 侧保证停车命令与退出/取消/失败时发零速
- Docker 镜像未在本机实际构建（Docker Hub 不可达），CI 中会构建验证
- 调度看门狗是兜底：正常失败由 agent 先报，看门狗只处理失联/卡死
- 集成测试覆盖 manager↔agent 契约，不覆盖 Nav2/感知；后者由 nightly 冒烟兜底
